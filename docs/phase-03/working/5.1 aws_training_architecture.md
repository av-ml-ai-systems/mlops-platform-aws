# AWS Training Architecture

## 1. Purpose and Scope

This document defines the initial AWS architecture for the training and model-management workflow developed in Phase 03 of the MLOps Engineering Roadmap.

Its purpose is to establish the responsibilities, integration, and execution flow of the main AWS services required to prepare training data, train candidate models, evaluate their performance, and preserve the resulting artifacts and experiment evidence.

The architecture focuses on the following AWS services and capabilities:

- Amazon SageMaker Processing Jobs.
- Amazon SageMaker Training Jobs.
- Amazon SageMaker Pipelines.
- Amazon SageMaker Experiments.
- Amazon S3.
- Existing AWS data infrastructure from Phase 02.

This document establishes the initial architectural design. It does not implement the infrastructure, deploy a model, or establish a production inference endpoint.

The architecture must remain consistent with the project's cost-control requirements, existing repository structure, and reproducibility objectives.

## 2. Architectural Context

The training architecture builds upon the data foundation established in the previous phases.

### 2.1 Phase 01 — Local Data and Feature Engineering

Phase 01 established the initial data-processing and feature-engineering capabilities.

Existing components include:

- Domain-oriented datasets for customer profiles, financial history, and loan applications.
- Data preprocessing and validation.
- Feature engineering modules.
- Offline feature generation.
- Dataset versioning and metadata management.
- The `build_features.py` script.

These components represent existing functionality that should be evaluated for reuse rather than automatically reimplemented in the AWS training workflow.

### 2.2 Phase 02 — AWS Data Foundation

Phase 02 established the initial AWS data infrastructure.

Relevant services and components include:

- Amazon S3 for persistent data storage.
- AWS Glue for ETL processing.
- AWS Glue Data Catalog for dataset metadata.
- Amazon Athena for querying curated data.
- Terraform for infrastructure provisioning.
- CloudWatch for AWS operational logs.

The curated loan-risk dataset is the initial training-data source.

The previously reviewed curated dataset contains the target variable:

`loan_outcome`

Where:

- `0` represents non-default.
- `1` represents default.

The training architecture must consume the curated dataset without unnecessarily duplicating the existing data-engineering workflow.

### 2.3 Architectural Principle

The initial design separates responsibilities:

- Data engineering prepares and publishes curated data.
- SageMaker Processing Jobs prepare and validate training inputs.
- SageMaker Training Jobs execute model training.
- SageMaker Pipelines orchestrates the workflow.
- SageMaker Experiments tracks experiment executions and results.
- Amazon S3 preserves datasets, artifacts, and supporting evidence.

This separation improves maintainability, traceability, and the ability to evolve individual components independently.

## 3. Architecture Overview

The proposed training architecture follows this conceptual workflow:

`Curated Dataset (Amazon S3)`

↓

`SageMaker Processing Job — Data Preparation and Validation`

↓

`SageMaker Processing Job — Dataset Splitting and Preprocessing`

↓

`SageMaker Training Job — Model Training`

↓

`SageMaker Processing Job — Model Evaluation`

↓

`SageMaker Pipeline — Evaluation and Acceptance Conditions`

↓

`Experiment Evidence and Model Artifacts (Amazon S3)`

`SageMaker Experiments` provides experiment tracking across the relevant executions.

The workflow will be orchestrated by SageMaker Pipelines.

The actual implementation may combine processing responsibilities into fewer jobs where doing so is technically appropriate. The architecture defines logical responsibilities rather than requiring a separate job for every operation.

## 4. SageMaker Processing Jobs

### 4.1 Purpose

SageMaker Processing Jobs execute data-processing and evaluation workloads independently of model training.

They provide managed execution environments for operations that prepare or evaluate model inputs and outputs.

### 4.2 Responsibilities

The initial architecture assigns Processing Jobs the following responsibilities:

**A. Training-data validation**

- Load the curated dataset from Amazon S3.
- Validate the expected schema.
- Verify the target variable.
- Check data types and missing values.
- Detect invalid or unexpected values.
- Generate validation evidence.

Existing validation logic should be reused or adapted where appropriate.

**B. Dataset preparation**

- Prepare the features required for training.
- Separate the target variable from the input features.
- Generate training, validation, and holdout test datasets.
- Preserve the splitting configuration.
- Ensure that the split process is reproducible.

**C. Preprocessing**

Depending on the selected model and feature types, preprocessing may include:

- Missing-value imputation.
- Categorical encoding.
- Numerical scaling.
- Other transformations required by candidate models.

Preprocessing parameters must be fitted using training data only, or the corresponding training folds during cross-validation.

The fitted preprocessing components must be preserved so that the same transformations can later be applied during inference.

**D. Model evaluation**

After training, a Processing Job may:

- Load the trained model artifact.
- Load the corresponding preprocessing components.
- Evaluate the model using validation or holdout test data.
- Generate classification metrics.
- Produce confusion matrices and evaluation reports.
- Compare results against predefined acceptance conditions.

### 4.3 Execution Environment

Processing Jobs will use managed CPU-based compute resources.

The initial design does not require GPU-based processing.

The exact instance type, processing image, dependencies, and resource configuration will be established during implementation planning.

### 4.4 Outputs

Processing Jobs may produce:

- Validated dataset outputs.
- Training, validation, and test splits.
- Preprocessing artifacts.
- Validation reports.
- Evaluation reports.
- Execution metadata.

Persistent outputs should be stored in Amazon S3.

Temporary intermediate data should be managed according to the artifact-retention strategy.

## 5. SageMaker Training Jobs

### 5.1 Purpose

SageMaker Training Jobs execute model-training workloads using the prepared datasets and selected training algorithms.

Their primary responsibility is to fit candidate models and generate model artifacts.

### 5.2 Responsibilities

Training Jobs will:

- Load the prepared training dataset.
- Load the required validation data when applicable.
- Apply the configured training algorithm.
- Execute model fitting.
- Record training configuration and hyperparameters.
- Preserve relevant training metrics.
- Generate the trained model artifact.

The training process must be consistent with the evaluation strategy defined in the `training_and_evaluation_strategy.md` document.

### 5.3 Initial Candidate Models

The initial candidate models are:

- Logistic Regression.
- Random Forest.
- Gradient-boosted trees, subject to dependency and environment constraints.

A simple baseline, such as a Dummy Classifier, should be included as a reference point.

The architecture must support comparing multiple candidate models without requiring a separate infrastructure design for each algorithm.

### 5.4 Training Outputs

A successful Training Job produces a model artifact, typically packaged as:

`model.tar.gz`

The artifact is stored in Amazon S3.

The training execution should also preserve:

- Model configuration.
- Hyperparameters.
- Training execution information.
- Software and dependency versions.
- Relevant training metrics.
- References to the dataset version used.

The trained model must remain associated with the preprocessing components required to process inference inputs correctly.

## 6. SageMaker Pipelines

### 6.1 Purpose

SageMaker Pipelines provides orchestration for the complete training workflow.

It connects the individual processing, training, and evaluation operations into a reproducible sequence of pipeline steps.

### 6.2 Responsibilities

The pipeline will coordinate:

1. Dataset validation.
2. Dataset preparation and splitting.
3. Model training.
4. Model evaluation.
5. Evaluation-based acceptance conditions.
6. Preservation of execution outputs and metadata.

The pipeline should define dependencies between steps so that subsequent operations execute only when their required inputs are available.

### 6.3 Initial Pipeline Structure

The proposed logical structure is:

**Step 1 — Data Validation**

A Processing Job validates the curated dataset and produces validation evidence.

**Step 2 — Data Preparation**

A Processing Job prepares features, creates dataset splits, and performs the required preprocessing.

**Step 3 — Model Training**

A Training Job trains the selected candidate model using the prepared data.

**Step 4 — Model Evaluation**

A Processing Job evaluates the trained candidate using the validation dataset.

**Step 5 — Acceptance Evaluation**

The pipeline evaluates whether the candidate satisfies the predefined technical acceptance conditions.

For example:

- Required evaluation metrics are available.
- The model satisfies the provisional performance thresholds.
- Required artifacts and metadata are present.

**Step 6 — Output Preservation**

The pipeline execution and its associated artifacts remain traceable through their execution metadata and S3 output references.

### 6.4 Pipeline Parameters

The architecture should support configurable parameters such as:

- Dataset S3 location.
- Dataset version identifier.
- Model algorithm.
- Random seed.
- Training configuration.
- Hyperparameters.
- Evaluation thresholds.
- Compute configuration.

These parameters should be supplied through controlled configuration rather than being unnecessarily hardcoded in processing and training scripts.

The detailed configuration-management strategy belongs to Task 6.

### 6.5 Pipeline Execution

Each pipeline execution should provide a traceable execution record.

This record should allow the project to identify:

- Which dataset was processed.
- Which processing and training steps were executed.
- Which configuration was used.
- Which candidate model was generated.
- Which evaluation results were produced.
- Whether the acceptance conditions were satisfied.

A pipeline execution does not automatically imply that a model is approved for deployment.

## 7. SageMaker Experiments

### 7.1 Purpose

SageMaker Experiments provides experiment-tracking capabilities for organizing and comparing model-training executions.

It complements SageMaker Pipelines by preserving information about individual experiments and their results.

### 7.2 Responsibilities

The initial experiment-tracking strategy should record:

- Experiment identification.
- Training execution information.
- Model algorithm.
- Hyperparameters.
- Random seed.
- Dataset version reference.
- Relevant software configuration.
- Training metrics.
- Evaluation metrics.
- Model artifact location.
- Experiment execution status.

The tracking structure should support comparison between candidate models and subsequent hyperparameter optimization.

### 7.3 Experiment Organization

The proposed logical organization is:

- One experiment representing the loan-default prediction modeling objective.
- Multiple trial or execution records representing individual training attempts.
- Relevant configurations and metrics associated with each execution.

Each candidate model or hyperparameter configuration should be identifiable independently.

Pipeline executions and experiment records should be associated where supported by the selected SageMaker integration.

The implementation must explicitly establish the required tracking relationships rather than assuming that every pipeline output automatically becomes a complete experiment record.

### 7.4 Relationship with Model Selection

Experiment tracking supports technical comparison, but it does not independently determine which model should be selected.

Model selection remains governed by the criteria established in the training and evaluation strategy.

Experiment tracking must preserve sufficient evidence to explain why a particular candidate was selected.

## 8. Amazon S3 Integration

### 8.1 Purpose

Amazon S3 provides persistent storage for training inputs, intermediate outputs where retention is required, model artifacts, and supporting evidence.

It acts as the central storage layer connecting the data foundation and the SageMaker training workflow.

### 8.2 Storage Responsibilities

The initial architecture identifies the following logical storage categories:

- Curated training datasets.
- Prepared training, validation, and test datasets.
- Processing outputs.
- Preprocessing artifacts.
- Training outputs.
- Evaluation reports.
- Experiment evidence.
- Model artifacts.
- Execution metadata and lineage references.

### 8.3 Storage Organization

The detailed S3 prefix structure will be established in the companion document:

`model_artifacts_and_experiment_lineage.md`

The architecture should maintain clear separation between:

- Persistent project data.
- Experiment outputs.
- Model artifacts.
- Temporary execution data.

Existing Phase 02 data locations should be reused where appropriate.

The implementation must avoid accidental overwriting of previous dataset versions or model artifacts.

## 9. End-to-End Workflow

The initial AWS training workflow is summarized below.

### Stage 1 — Data Availability

The curated loan-risk dataset is available in Amazon S3 following the Phase 02 data-engineering process.

Its dataset version and metadata provide the starting point for training-data traceability.

### Stage 2 — Data Validation

A SageMaker Processing Job reads the curated dataset and performs the required validation checks.

Invalid data should prevent the workflow from proceeding to model training.

### Stage 3 — Data Preparation

A Processing Job prepares the model features, creates the required dataset splits, and performs preprocessing.

The transformations and resulting datasets must be traceable to the original curated dataset.

### Stage 4 — Model Training

A SageMaker Training Job trains a candidate model using the prepared training data.

The execution configuration and model artifact are preserved.

### Stage 5 — Model Evaluation

A Processing Job evaluates the candidate using the validation dataset.

The evaluation results are recorded and compared against the predefined criteria.

Final holdout test evaluation must remain separate from repeated candidate tuning.

### Stage 6 — Experiment Tracking

SageMaker Experiments records the relevant experiment information and enables comparison between training executions.

### Stage 7 — Candidate Assessment

The pipeline evaluates the technical acceptance conditions.

A candidate that does not satisfy the required conditions should not proceed to the next lifecycle stage as an accepted model.

### Stage 8 — Artifact Preservation

The model artifact, preprocessing components, evaluation evidence, and lineage information are preserved in their corresponding storage locations.

### Stage 9 — Model Lifecycle Handoff

A technically acceptable candidate may become eligible for model registration and subsequent approval.

Registration, approval, and deployment remain separate lifecycle decisions.

Production deployment is outside the scope of this task.

## 10. Architectural Constraints and Design Principles

The initial architecture must respect the following constraints.

### 10.1 Cost Control

- Prefer CPU-based compute for the initial tabular classification workload.
- Avoid GPU infrastructure unless a demonstrated technical requirement justifies it.
- Use temporary compute resources where appropriate.
- Avoid continuously running endpoints during training development.
- Configure resource sizes and execution limits according to workload requirements.
- Preserve outputs before deleting temporary resources.

### 10.2 Existing Component Reuse

The architecture should reuse relevant functionality from:

- Phase 01 feature-engineering modules.
- Existing dataset validation logic.
- Dataset versioning and metadata utilities.
- Phase 02 curated-data publication.
- Existing Terraform infrastructure.

Reuse must be based on technical compatibility, not simply on the existence of a component.

### 10.3 Separation of Responsibilities

Data preparation, training, orchestration, experiment tracking, and artifact storage must remain logically distinct.

This separation should allow individual components to evolve without requiring unnecessary redesign of the entire workflow.

### 10.4 Reproducibility

Every training execution should be associated with sufficient dataset, configuration, software, and experiment information to support reproducibility.

Detailed reproducibility controls are addressed in Task 6.

The following questions must be resolved before or during implementation:

1. Which existing preprocessing and feature-engineering modules can be reused directly in SageMaker?
2. Does the current feature schema require an adapter before the curated dataset can enter the training workflow?
3. Should data validation and preprocessing be implemented as separate Processing Jobs or combined?
4. What is the appropriate S3 prefix structure?
5. Which SageMaker SDK version and integration approach will be used?
6. How should SageMaker Experiments be associated with pipeline executions?
7. At what point should SageMaker Model Registry be introduced?

These decisions should be made without unnecessarily expanding the initial architecture.
