# Model Artifacts, Experiment Evidence and Dataset Lineage

## 1. Purpose and Scope

This document defines the initial strategy for preserving model artifacts, experiment evidence, and dataset lineage within the Phase 03 AWS training architecture.

Its purpose is to ensure that every relevant training execution can be traced to its input dataset, processing configuration, training configuration, evaluation results, and resulting model artifacts.

The strategy uses Amazon S3 as the primary persistent storage layer and integrates with SageMaker Processing Jobs, SageMaker Training Jobs, SageMaker Pipelines, and SageMaker Experiments.

The document establishes the initial artifact lifecycle and traceability requirements.

Detailed infrastructure provisioning, configuration management, resource ownership, and cleanup procedures will be further defined in Task 6.

## 2. Dataset Lineage

### 2.1 Purpose

Dataset lineage establishes the origin and transformation history of the data used in model training.

The training workflow must be able to identify which dataset version was used to generate a particular model artifact.

This is particularly important because the project already implements dataset versioning and metadata management in Phase 01.

### 2.2 Existing Dataset Versioning

The existing repository includes a dataset-versioning utility:

`src/mlops_engineering_roadmap/utils/versioning.py`

The reviewed functionality includes:

- SHA-256 content hashing.
- Dataset metadata.
- UTC timestamps.
- Version identification.
- Atomic YAML metadata persistence.
- Protection against immutable-version overwriting.

The existing versioning mechanism should remain the primary reference for dataset-version identification where applicable.

It should not be confused with experiment tracking or model registration.

### 2.3 Curated Dataset Lineage

The initial training workflow consumes the curated loan-risk dataset published through Phase 02.

Its lineage should preserve references to:

- The source dataset.
- The curated dataset location.
- The dataset version.
- The dataset content hash, where available.
- The publication metadata.
- Relevant validation outcomes.
- The processing execution that consumed the dataset.

The lineage information must make it possible to trace a model-training execution back to its original curated input.

### 2.4 Dataset Transformation History

When the curated dataset is transformed for training, the workflow should preserve the relationship between:

`Curated Dataset → Prepared Dataset → Training Dataset`

The metadata should identify:

- The source dataset version.
- The processing operation.
- The transformation configuration.
- The resulting dataset location.
- The execution identifier.
- The creation timestamp.

Prepared datasets must not be treated as independent, unexplained data sources.

Their relationship with the original curated dataset must remain explicit.

## 3. Processing Artifacts

### 3.1 Purpose

Processing artifacts are the outputs generated by SageMaker Processing Jobs.

They provide evidence of the data preparation and validation operations performed before and after model training.

### 3.2 Expected Outputs

The initial workflow may preserve the following processing outputs:

**A. Data validation outputs**

- Validation reports.
- Schema validation results.
- Missing-value summaries.
- Data-quality findings.
- Validation execution metadata.

**B. Dataset preparation outputs**

- Training dataset.
- Validation dataset.
- Holdout test dataset.
- Feature and target separation information.
- Dataset-splitting metadata.

**C. Preprocessing outputs**

- Fitted preprocessing components.
- Transformation configuration.
- Relevant feature metadata.
- Preprocessing execution information.

**D. Model evaluation outputs**

- Evaluation metrics.
- Confusion matrices.
- Classification reports.
- Evaluation summaries.
- Acceptance-condition results.

### 3.3 Preprocessing Consistency

The preprocessing components used during training must remain associated with the resulting model.

For example, if the training workflow uses imputation, categorical encoding, and numerical scaling, the fitted transformations must be preserved.

The inference workflow must apply compatible transformations in the correct order.

The model artifact and its required preprocessing components must therefore be treated as a coherent deliverable.

## 4. Experiment Evidence

### 4.1 Purpose

Experiment evidence provides the information necessary to understand, compare, and reproduce model-training executions.

SageMaker Experiments will provide the experiment-tracking capability, while Amazon S3 will preserve relevant output artifacts and reports.

These capabilities are complementary rather than interchangeable.

### 4.2 Required Experiment Information

Each training execution should preserve the following information.

| Category | Information |
|---|---|
| Experiment identification | Experiment name and execution/trial reference |
| Dataset | Dataset version, S3 location, and hash where available |
| Model | Algorithm and model configuration |
| Training | Training parameters and hyperparameters |
| Reproducibility | Random seed and relevant software versions |
| Execution | Pipeline and Training Job references |
| Performance | Training and evaluation metrics |
| Evaluation | Confusion matrix and classification report |
| Output | Model artifact S3 location |
| Preprocessing | Preprocessing artifact and configuration references |
| Selection | Candidate-selection rationale and outcome |

The exact metadata schema will be defined during implementation.

### 4.3 Experiment Comparison

The tracking strategy should support comparisons between candidate models.

For the initial loan-default prediction use case, comparisons should include:

- Default-class recall.
- Default-class precision.
- PR-AUC.
- F1 score.
- ROC-AUC.
- Confusion matrix.

The primary and secondary metrics must follow the established training and evaluation strategy.

Experiment results must be associated with their corresponding dataset and training configurations.

A metric without its execution context is insufficient for meaningful comparison.

### 4.4 Hyperparameter Optimization Evidence

When hyperparameter optimization is introduced, the workflow should preserve:

- Search-space definition.
- Trial configuration.
- Trial identifier.
- Random seed where applicable.
- Evaluation metric.
- Trial results.
- Best candidate configuration.
- Relevant execution information.

The purpose is to make the optimization process auditable rather than preserving only the final winning configuration.

## 5. Model Artifacts

### 5.1 Purpose

Model artifacts are the outputs generated by successful training executions.

They must be stored persistently and remain associated with the experiment and dataset information that produced them.

### 5.2 Required Model Outputs

The initial model artifact package should include:

**A. Trained model**

The serialized model produced by the SageMaker Training Job.

A typical SageMaker model artifact is packaged as:

`model.tar.gz`

**B. Preprocessing components**

The fitted transformations required to prepare inference inputs.

These may include:

- Imputation objects.
- Encoders.
- Scalers.
- Feature transformation components.

**C. Model metadata**

Metadata should identify:

- Model name or identifier.
- Model version or candidate identifier.
- Algorithm.
- Training execution reference.
- Dataset version.
- Training configuration.
- Software environment.
- Creation timestamp.
- Evaluation results.
- Artifact location.

**D. Evaluation evidence**

The model should remain associated with the evaluation reports that support its technical assessment.

### 5.3 Model and Preprocessing Consistency

The trained model must not be separated from the preprocessing logic required to interpret its inputs correctly.

The artifact lifecycle must preserve their compatibility.

A model that cannot be loaded or applied with its required preprocessing components is not considered a complete training deliverable.

### 5.4 Model Candidate Preservation

Multiple candidates may be generated during training and experimentation.

The strategy should preserve relevant candidate artifacts and their evaluation evidence according to the project's retention policy.

Previous candidates should not be silently overwritten when a new training execution occurs.

This supports comparison, auditing, and controlled model selection.

## 6. Amazon S3 Artifact Organization

### 6.1 Purpose

Amazon S3 will provide the persistent storage layer for dataset references, processing outputs, experiment evidence, and model artifacts.

The storage structure should make it possible to identify the relationship between the different workflow stages.

### 6.2 Proposed Logical Structure

The following is an initial logical organization proposal:

` s3://<project-bucket>/`

- `datasets/`
  - `curated/`
  - `prepared/`
  - `training/`
  - `validation/`
  - `test/`

- `processing/`
  - `validation-reports/`
  - `preprocessing/`
  - `evaluation/`

- `experiments/`
  - `<experiment-id>/`
    - `<execution-id>/`
      - `configuration/`
      - `metrics/`
      - `reports/`
      - `metadata/`

- `models/`
  - `<model-name>/`
    - `<candidate-id>/`
      - `model/`
      - `preprocessing/`
      - `metadata/`
      - `evaluation/`

This structure is conceptual and must be adapted to the final implementation.

It does not imply that every SageMaker-generated artifact will automatically follow these prefixes.

SageMaker services may generate outputs in configured S3 locations. The implementation must explicitly configure and document the required locations.

### 6.3 Naming and Identification

Storage paths should use stable identifiers where appropriate.

Relevant identifiers include:

- Dataset version.
- Pipeline execution ID.
- Experiment ID.
- Training Job name.
- Candidate model ID.
- Model version.

Timestamps may supplement these identifiers but should not be the only means of identifying an artifact.

### 6.4 Immutability and Overwriting

Previously generated dataset versions and model candidates should remain identifiable.

The storage strategy should avoid accidental overwriting of valuable outputs.

Where appropriate, unique execution identifiers and versioned prefixes should be used.

The exact S3 versioning and retention configuration will be decided during infrastructure planning.

## 7. Traceability and Relationships

### 7.1 Purpose

Traceability connects the data, processing, training, evaluation, and model-management stages.

The objective is to reconstruct the history of a model candidate from its original dataset.

### 7.2 Traceability Chain

The proposed relationship is:

`Dataset Version`

↓

`Processing Job Execution`

↓

`Prepared Dataset and Preprocessing Artifacts`

↓

`Training Job Execution`

↓

`SageMaker Experiment Record`

↓

`Model Artifact`

↓

`Evaluation Report`

↓

`Candidate Selection Decision`

Each stage should preserve references to the relevant upstream and downstream artifacts.

### 7.3 Minimum Traceability Requirements

For every candidate model, the workflow should be able to answer:

1. Which original dataset version was used?
2. Where did the training data come from?
3. Which processing operations were applied?
4. Which preprocessing configuration was used?
5. Which model algorithm and hyperparameters were selected?
6. Which training execution generated the model?
7. Which software environment was used?
8. Which evaluation metrics were obtained?
9. Where is the model artifact stored?
10. Why was the candidate selected or rejected?

The traceability mechanism should combine repository metadata, SageMaker execution information, experiment records, and S3 artifact references.

No single service should be assumed to contain every piece of required evidence.

## 8. Model Lifecycle and Governance

### 8.1 Candidate Model

A candidate model is an artifact generated by a training execution.

It must have associated configuration, dataset lineage, and evaluation evidence.

Generating a candidate does not mean that it satisfies the technical acceptance criteria.

### 8.2 Model Registration

A technically acceptable candidate may become eligible for registration in SageMaker Model Registry.

Registration provides a structured mechanism for managing model versions and their associated metadata.

The exact registry integration will be established in the implementation design.

### 8.3 Model Approval

Model approval is a separate governance decision.

A registered candidate should not automatically be considered approved for deployment.

Approval must follow the project's defined evaluation and governance criteria.

### 8.4 Deployment

Deployment is a separate lifecycle stage that makes an approved model available for inference.

Production deployment is outside the scope of this document and the current Task 5 implementation.

The important distinction is:

`Training → Evaluation → Candidate Selection → Registration → Approval → Deployment`

These stages must remain conceptually and operationally separate.

## 9. Retention and Cleanup

### 9.1 Persistent Evidence

The following outputs should be preserved as persistent project evidence:

- Dataset versions and metadata.
- Relevant lineage information.
- Processing validation reports.
- Experiment configurations and results.
- Model artifacts selected for preservation.
- Preprocessing components.
- Evaluation reports.
- Model metadata.
- Relevant architectural and selection decisions.

### 9.2 Temporary Resources

Not every AWS resource needs to remain active after an execution.

Temporary resources may include:

- Processing compute instances.
- Training compute instances.
- Temporary pipeline execution resources.
- Intermediate data that is no longer required.
- Other execution-related infrastructure.

Temporary infrastructure must not be confused with persistent evidence.

### 9.3 Mandatory Preservation Before Cleanup

Before destroying temporary infrastructure or deleting temporary data, the workflow must:

1. Identify the outputs that must be preserved.
2. Verify that the relevant S3 artifacts exist.
3. Verify that model artifacts can be accessed.
4. Verify that evaluation reports and metadata are complete.
5. Preserve the required evidence locally where appropriate.
6. Confirm that no valuable output depends on infrastructure scheduled for deletion.

Cleanup must never destroy the only copy of a required model artifact or experiment record.

### 9.4 Retention Policy

The exact retention periods, S3 lifecycle rules, and deletion policies remain open decisions.

They will be addressed in Task 6 together with the broader infrastructure lifecycle.

The initial principle is to preserve valuable project evidence while minimizing unnecessary cloud-storage and compute costs.

## 10. Assumptions and Open Decisions

The following assumptions guide the initial artifact and lineage strategy.

| Area | Initial Proposal | Status |
|---|---|---|
| Persistent storage | Amazon S3 | Established architectural choice |
| Dataset versioning | Reuse existing repository utility and metadata | Established design direction |
| Experiment tracking | SageMaker Experiments | Proposed |
| Training outputs | SageMaker Training Job artifacts in S3 | Proposed |
| Processing outputs | S3-based outputs and reports | Proposed |
| Model artifacts | Serialized model plus required preprocessing components | Established requirement |
| Traceability | Dataset, processing, training, and experiment references | Established requirement |
| Model registration | SageMaker Model Registry | To be evaluated |
| S3 prefix structure | Dedicated logical prefixes | Proposed |
| S3 versioning | Evaluate during infrastructure design | Pending |
| Artifact retention | Preserve valuable outputs before cleanup | Established requirement |
| Lifecycle policies | Define in Task 6 | Pending |

The following questions remain open:

1. Should model and preprocessing components be packaged together or stored separately with explicit references?
2. Which metadata should be stored in SageMaker Experiments and which should be preserved as repository-generated JSON or YAML?
3. Should S3 bucket versioning be enabled for the artifact locations?
4. Which experiment outputs should be retained for every trial?
5. How should unsuccessful training executions be handled?
6. What is the minimum evidence required before a candidate becomes eligible for registration?
7. Which artifacts must be copied or backed up locally before AWS cleanup?

These decisions should be resolved progressively without introducing unnecessary complexity into the initial implementation.

## 11. Task 5 Acceptance Criteria

The artifact and lineage strategy will be considered documented when:

- Dataset lineage requirements are established.
- The relationship between curated and prepared datasets is defined.
- Processing outputs and validation evidence are identified.
- Required experiment configurations and results are defined.
- Model artifacts and preprocessing components are treated as a coherent deliverable.
- A proposed S3 organization is documented.
- Traceability between dataset versions, processing executions, training executions, experiments, and model artifacts is established.
- Model registration, approval, and deployment are distinguished.
- Persistent evidence is separated from temporary infrastructure.
- Preservation requirements before AWS cleanup are established.
- Remaining assumptions and architectural decisions are explicitly identified.

Completion of this document does not imply that artifact storage, experiment tracking, or model registration has already been implemented.

It establishes the requirements and design direction for subsequent implementation.
